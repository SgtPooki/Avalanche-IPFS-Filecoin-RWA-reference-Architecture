The token is immutable. The evidence behind it usually is not.

Most tokenized assets point at a URL. A URL says where a file is today. It does not say whether it is the same file, whether it changed, or whether it will be there next year.

URL in token metadata
Anyone who controls the server can swap the file.
Hash in an internal database
Only the issuer can check it.
Nothing
The token trades on trust in the issuer's infrastructure.

What lives where

Avalanche stores a pointer. Filecoin stores the documents. Nothing else crosses between them.

Avalanche Fuji

A pointer, per asset

a few hundred bytes, onchain
  • the asset id, BAL-PROP-001
  • the CID of the current manifest
  • that manifest's Filecoin piece CID and data set id
  • one appended entry per version, never overwritten
Filecoin Calibration

The documents themselves

every file, addressed by its IPFS CID
  • manifest.json, which lists every record by CID
  • deed.pdf, parcel.json, survey.pdf, the tax assessments
  • stored as pieces that providers keep proving they still hold

No document bytes are written to Avalanche, and no Avalanche state is written to Filecoin. The only thing shared is the CID.

What a verifier actually checks

Four claims, in order. Each is checked against a different system, and a failure of any one fails the record.

Avalanche points at this manifest
Read the manifest CID off the registry for the asset. This is the issuer's claim, and it is the only thing they signed.
The manifest is the one it points at
Fetch it, hash the bytes, and check the CID comes out the same. A manifest that hashes differently is not the anchored one.
Every record is the one the manifest lists
Fetch each file, hash it, compare to the CID in the manifest. A changed deed produces a different CID and fails here.
Filecoin still holds them
Read the proof state for the data set. It says when possession was last proven and when the next proof is due.

No single point of trust

Three questions, each answered by a different system. None of them has to trust the others.

Avalanche
Which record set belongs to this asset?
The registry stores the manifest CID on the asset. One transaction per version.
IPFS
What does that record set contain?
Each file's CID is a fingerprint of its bytes. Change one character and the CID changes.
Filecoin
Are the files still stored?
Storage providers post proofs of possession on a schedule anyone can check.

Building on the 2025 Avalanche and Filecoin bridge

Ava Labs and the Filecoin Foundation connected the two networks in May 2025 with a cross-chain data bridge that confirmed Filecoin storage deals on Avalanche. This template takes the next step for asset records.

Proofs on a schedule
Storage providers keep proving possession. The record shows when the last proof happened and when the next one is due.
One CID per record set, with history
Every version is anchored on Avalanche. Updates add a version. A changed file fails.
Direct verification
Anyone reads Avalanche and Filecoin directly. No extra service in between.

Change one line in a deed and verification fails

Same filename, different owner line, different fingerprint. The registry never pointed at the second file, so it fails.

Tampering vs update

Tampering
The bytes of a document changed, but the CID on Avalanche did not. The new bytes hash to a different CID, so the check fails.
Update
New bytes, a new manifest CID, and a new version written to Avalanche. Both versions still verify, each against its own CID.

Design notes · screen 1

  • Category first. Headline names the category (verifiable offchain records), the value, and the who (Avalanche RWA issuers) before any feature.
  • Order follows the sales narrative: problem, what issuers do today including do-nothing, what a fix looks like, tamper proof, then the offer.
  • Identity: Anchor line. One rule from Avalanche red through the record into Filecoin blue. The record card is the hero object. Schibsted Grotesk, IBM Plex Sans, IBM Plex Mono.
  • Light by default, and it ignores the system setting. Team feedback on the boards preferred the county-clerk read over the black and neon ones. Accents are held back on light: Avalanche #B32A2B, Filecoin #0062B8, IPFS #378085, verified #178F5A, failed #B8760F. Dark is still there under data-theme="dark" at full strength.
  • Positioning from the prior-art research. Credit the May 2025 Avalanche and Filecoin bridge, then the three additions. Never claim to be first. Do not grade the earlier work here. "Built on Avalanche" wording only, no logos.
  • "Fork the template" points at github.com/SgtPooki/anchorline.
  • QIs a partner logo row (Avalanche, Filecoin) wanted here, or does that need clearance first?
  • Registry, not token. The form writes one registry entry. Do we want a token visual anywhere for the Avalanche audience, or is "asset" enough?
  • Env key, no wallet connect. Top-right shows an address but there is no connect flow. Shared key funds both Fuji and Calibration. Gemini suggested a "Connect Core Wallet" opener; rejected, it adds a flow the template does not ship.
  • Transaction moment. Chain writes show a 1.5s signing overlay in the chain color so the audience sees the write happen. Skipped under reduced motion.
  • Asset type dropdown keeps vehicle and equipment. Zero-cost signal that the pattern generalizes beyond real estate (Gemini round 2 agreed).
  • One upload per file. Each record gets its own CID and its own Filecoin status so the per-record checks later are honest.
  • Status vocabulary: Uploading → Committing onchain → Proving. "Proving" is the resting state. Avoids claiming a fresh proof that has not landed.
  • QShow piece CIDs in this table too, or keep them in the manifest only?
  • Manifest is a first-class object. Shown raw on purpose, in the canonical form the bytes are hashed in: keys sorted at every depth, and the real CIDs of the committed dataset. Engineers will want the schema, not a summary.
  • Anchor writes three things: manifest CID, its piece CID, and data set ID. The registry appends the version itself, which is why the manifest does not carry one; a number inside the document could disagree with the chain. That makes a verifier self-sufficient from the Avalanche record.
  • QIs showing the "Who vouches for what" panel here too early, or is this exactly where the story lands?
  • Two cards, two chains. Onchain asset is red-tagged Avalanche, storage is blue-tagged Filecoin. The color rule holds across every screen.
  • Proof fields in plain words. "Last proof 38 min ago", "next proof due in 23 h", with epoch numbers demoted to muted mono. Explorer link reads "Storage proofs".
  • QDo we want a property image on this page? PRD lists property.jpg. Cursor's review suggested cutting it first if time is short.
  • Verdict first, evidence below. The 30-second read is the banner plus the four summary checks. Per-record table is for the engineer.
  • No wallet on this view. It reads Fuji and Filecoin, and hashes in the browser. That is the "anyone can verify" claim made visible.
  • QRetrieval path: Synapse download by piece CID (reliable) vs public IPFS gateway (better story). Mockup does not commit either way.
  • Tamper is a local file check. Gateways will not serve tampered bytes, so the honest scenario is "someone handed me this PDF". The file never leaves the browser.
  • Amber, not Avalanche red. Failure is amber in both themes so the brand color never means "bad".
  • Owner-line diff stays. It is the "aha" for a non-technical viewer. Needs PDF text extraction in the build; the disclaimer covers the illustrative case.
  • Timeline from events. History is read straight from registry events. No indexer, which keeps the fork simple.
  • Changed rows are marked. Only the tax assessment differs between v1 and v2, and it says so.
  • "Publish new version" reopens the upload step pre-filled. A separate diff flow is overkill for the demo.
